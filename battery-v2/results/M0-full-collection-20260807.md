## Concurrent-session incident (PREREG r7 DEFECT4, mechanism record)

Commit history for this worktree contains a duplicate-looking batch8 pair: `1da8311` (wrote all 90/90 B-DE-none_clinical-sonnet lanes + coded-de.tsv + dispatch-map + raw files) followed 1 second later by `535b5a4` (same nominal batch, but its diff is ONLY +2 dispatch-map rows, `git diff 1da8311 535b5a4 --stat` = 1 file, 2 insertions -- verified by re-running that diff, not asserted from memory). Root cause: the 30-minute room timeout ends the ROOM, not the dispatcher subprocess it launched; a relaunch after timeout starts a second writer against the same on-disk worktree/dispatch-map while the first writer's background process is still finishing. **Data integrity was not compromised**: independently re-verified on the full 900-row `runs/run-20260807-fullscale/dispatch/dispatch-map.tsv` -- 900 data rows, 0 duplicate lane_id, 0 duplicate room_id (re-measured via `sort|uniq -d`, not carried over from a prior claim). **What made this safe (mechanism, so it's reproducibly safe next time, not just lucky)**: (1) `dispatch_lanes.py` loads already-dispatched lane_ids from the existing dispatch-map before dispatching and skips any lane_id already present -- a second writer resuming the same manifest can only ever dispatch the REMAINING undispatched lanes, never re-dispatch or overwrite one already claimed. (2) `code_outputs.py`'s `validate_dispatch_map()` refuses (exit 1, writes nothing) if any room_id maps to more than one lane_id or any lane has zero/multiple dispatch-map entries -- so even if two writers HAD raced on the same lane_id, coding would hard-fail rather than silently accept ambiguous provenance. Both are pre-existing design properties (PREREG r3 DEFECT4 / 弁勁L5), not new code written to fix this incident -- this was a **designed idempotency property that happened to be exercised**, not luck.
